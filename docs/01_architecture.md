# 整体架构与模块职责

## 系统目标
PC或Linux升级工具通过经典CAN（500 kbit/s）、ISO-TP和UDS向STM32F407上的常驻Bootloader发送固件。Bootloader负责Flash擦写、读回、校验、有效性提交及APP启动选择。基础版不包含联网OTA或自动回滚。

## 分层关系

| 模块 | 职责 | 当前状态 |

| 升级工具 | 读取固件文件、计算校验值、发送诊断请求、提示进度和超时 | 待实现 |
| CAN驱动 | bxCAN过滤、接收、发送、错误处理 | 待移植 |
| ISO-TP | 单帧/首帧/连续帧/流控、序号、块大小、帧间隔及超时 | 待集成 |
| UDS服务端 | 会话控制、下载、分块传输、校验和诊断负响应 | 待实现 |
| 固件更新核心 | 擦除、顺序写入、读回和提交 | 已实现，主机端验证 |
| 镜像验证 | 检查元数据、向量表与整包CRC后决定是否启动 | 已实现，主机端验证 |
| STM32 Flash适配 | 实际扇区擦除、编程、读回及错误码 | 待实现 |
| Bootloader启动 | 时钟、看门狗、中断清理、MSP/VTOR和APP跳转 | 待实现 |
| APP业务程序 | 版本信息、业务演示、进入升级模式 | 待实现 |

## 不可破坏的约束
1. 升级命令不得擦除Bootloader所在的扇区0～3。
2. 开始下载时先清除旧元数据，避免未完成的程序被当作有效固件。
3. 只允许写入声明范围内的连续固件字节，并在写入后读回核对。
4. 整包CRC匹配后才能提交元数据；有效提交标志最后写入。
5. 每次启动时重新检查元数据、复位向量和固件内容。
6. 单槽升级失败时旧APP可能不可用，但应保留Bootloader作为恢复入口。
7. CAN中断只负责及时接收，耗时Flash操作在前台状态机处理。

## 启动决策
复位 → 初始化 → 检查固件元数据与CRC → 有效且无升级请求则跳转APP；否则进入常驻Bootloader等待重新刷写。

**证据层级：** 设计推导、主机单元测试、协议联调、ARM交叉编译、实物测试应分别记录。任何一层不能代替其他层。
