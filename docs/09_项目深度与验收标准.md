# 项目最终交付物、完成判断与证据标准

> 目标：形成一套针对 **STM32F407 的 CAN/ISO-TP/UDS 在线固件升级**工程：有完整可交叉编译的 Bootloader、APP、升级工具和可追溯的开发过程，技术细节符合芯片实际条件，能够结合源码回答嵌入式软件面试追问。**不要求购买实物，也不强制搭建芯片仿真环境**。没有实物不妨碍合理进行公开资料调研、理论分析、交叉编译、反汇编检查和能开展的软件测试，但不能把这些写成硬件实测。

## 一、最终必须交付的五项成果

| 交付物 | 最低完成条件 | 对应面试用途 |
|---|---|---|
| **1. 完整、分层的工程源码** | Bootloader、APP、STM32F407 Flash驱动、bxCAN接口、ISO-TP、UDS升级服务、PC/Linux升级工具；不能只有头文件、空函数或架构图。具有真实芯片启动文件、完整链接脚本，能用ARM交叉工具链完成编译和链接 | 打开工程，讲清从固件文件到Flash写入、校验、启动的完整调用链 |
| **2. 清晰的中文README与架构说明** | 项目背景、使用场景、模块关系、Flash分区、协议时序、构建方法、关键命令、可复用代码来源、当前完成状态及验证边界 | 面试官第一眼理解项目的实际内容与贡献 |
| **3. 开发过程与测试记录** | 阶段性Git提交、设计取舍、真实构建日志、编译告警处理、可执行的软件测试与结果，失败情形及修复记录 | 证明不是拼接代码、只有功能清单 |
| **4. 2～3个深入的故障排查案例** | 每个记录：触发条件→现象或静态发现→最小复现/定位→根因→代码修改→复查或回归；必须可指向实际文件、差异与证据 | 应对“遇到什么问题、怎么定位、为什么这样修改” |
| **5. 关键参数与面试技术手册** | MCU/Flash/RAM、链接地址、程序体积、CAN波特率与报文配置、ISO-TP块大小/间隔/超时、UDS服务、最坏情况或吞吐估算，说明参数的来源与适用条件；面试追问能对应源码 | 应对底层原理、参数依据、性能瓶颈与工程取舍 |

**判定：** 这五项全部达到最低条件后，才可称为“工程源码和面试材料完整”。功能完成不等于硬件验证完成。

## 二、必做功能边界：以个人项目规模为准

### 必做：单APP槽位、可重新刷写的Bootloader

1. 固定Bootloader区、元数据区、APP区，防止升级时擦除Bootloader；链接地址和STM32F407真实Flash扇区一致。
2. 固件升级流程：编程会话、请求下载、分块传输、结束传输、Flash写入/读回、整包校验、有效性提交及重启。
3. CAN、ISO-TP与UDS分层；处理数据块乱序、重复请求、流控、超时、无效长度、非法地址与失败中止。
4. Bootloader根据镜像元数据、初始MSP、复位向量和CRC决定跳转APP或留在恢复入口。
5. APP至少包含可辨认的版本信息和基本业务行为；上位机可发起升级并查询反馈。
6. 单槽失败后通过常驻Bootloader **重新刷写**；不能将此称为自动回滚。

### 非必做/可选

- 软件A/B双APP槽及启动失败自动回滚；
- 数字签名、安全启动、固件加密；
- 云端OTA、AUTOSAR架构、量产安全认证；
- 漂亮的上位机图形界面；
- 实物硬件购买、完整仿真平台。

增加上述项目必须能带来明确的技术增量，不能为堆砌功能而增加。

## 三、没有实物时，允许且鼓励做什么

**不强制搭建仿真。** 技术分析可以采用以下证据，且必须区分：

| 类型 | 可接受做法 | 最终如何标记 |
|---|---|---|
| **原厂资料** | 查STM32F407数据手册、RM0090、官方应用笔记；确定Flash扇区大小、存储器组织、编程粒度、CAN资源与限制 | “原厂规格/官方资料” + 文件或网页链接及版本 |
| **公开工程数据** | 查GitHub真实开发记录、工程日志、官方演示、论文中的固件大小、升级耗时、吞吐或故障现象 | “第三方参考数据”，注明芯片、工具链、波特率、文件大小、测试环境与来源；**不得转述成我们的实测** |
| **理论分析** | 根据CAN帧有效数据、协议开销、波特率、固件大小及Flash时序计算吞吐率、传输时间、存储占用、缓存上界；明确公式和假设 | “理论估算”，给出假设、推导、结果范围和可能误差 |
| **代码级验证** | ARM交叉编译、链接映射、objdump反汇编、静态检查、单元测试、实际故障注入后回归 | “编译/静态检查/软件测试”，保留工具版本、命令和日志 |
| **未开展的板级行为** | 对实际Flash操作、CAN时序、中断阻塞、断电恢复提出技术上有依据的预期及验证步骤 | “待硬件验证”，不能虚构运行波形、故障寄存器或实测时间 |

### 估算参数的实际要求

- **固件大小和内存占用**：优先使用 ARM 编译输出的 `size`、`map`，记录编译器、优化级别、构建配置及提交号；不能拿第三方项目体积当作本项目编译结果。
- **CAN升级速度**：用总线波特率、帧长、ISO-TP有效载荷、流控与往返等待时间建立模型，分别报告“不计等待的理论上界”和“带合理假设的估算”；必须注明不是实测吞吐。
- **Flash擦除/编程时间**：可引用对应芯片原厂手册的典型/最大参数，分清工况及电压/温度条件；不允许凭空写出精确毫秒数。
- **故障现象**：可以参考公开案例，并主动在代码层引入类似错误研究根因；真实运行得到的结果称“本项目复现”，未复现的称“参考案例/潜在风险分析”。

## 四、技术深度的最低标准

| 技术主线 | 应能讲清楚 | 实际交付的证据 |
|---|---|---|
| **Cortex-M启动与APP跳转** | 复位向量、初始MSP、VTOR、中断/SysTick清理、跳转函数汇编和HardFault可能成因 | 独立APP链接脚本、跳转源码、反汇编或构建证据 |
| **Flash驱动与元数据** | STM32F407扇区划分、擦写对齐、地址防护、元数据最后提交、单Bank读写约束 | 芯片参数引用、Flash实现、异常路径代码及相关测试 |
| **ISO-TP与UDS刷写** | SF/FF/CF/FC、流控、STmin/BS、超时；0x10/0x34/0x36/0x37/0x31等服务与状态机 | 协议接口代码、请求应答示例、异常检查与日志 |
| **可靠性与恢复** | CRC与签名区别、错误块号、响应丢失、重复块幂等、下载中断如何恢复 | 事务状态图、恢复入口、可复现故障案例 |
| **工程取舍** | 为什么选择单APP槽、为何如此分区、为何中断里不直接擦Flash、缓冲与等待响应如何协调 | 至少三项设计对比或推导记录 |

## 五、开发故障案例的要求

至少两个、争取三个有实际分析深度的案例，优先从下面筛选：

1. **APP启动跳转**：MSP切换后的函数尾部、VTOR、SysTick或中断状态；依据编译结果、反汇编或实际可复现的软件行为定位。
2. **UDS/ISO-TP状态机**：连续帧序号异常、流控超时、0x36响应丢失和重复块造成的状态不一致；通过实际协议代码与测试处理。
3. **Flash和升级事务**：非法擦除区、部分写入、固件CRC不一致、元数据提交中止等；通过源码、故障注入和回归检查解决。

统一记录：**问题背景—复现输入—观察结果（或静态证据）—分析步骤—根因—修改差异—复查结果—证据局限。**

允许主动构造故障，也允许参考已有工程的真实案例；但必须讲清哪些问题由本项目实际发现或复现、哪些仅作案例研究。不得将不存在的硬件寄存器读数或实物观测写成亲测。

## 六、如何最终判断“项目完成，可以用于面试”

- [ ] Bootloader、APP、Flash、CAN/ISO-TP/UDS和上位机有**完整源码及真实接口连接**。
- [ ] 有STM32F407工具链生成的实际编译、链接、程序体积与映射结果。
- [ ] 主要协议与升级流程有可复查的软件级正常/异常验证；若存在未验证环节，明确列为风险。
- [ ] 五项交付物齐全，README中能导航到实际源码、日志和故障案例。
- [ ] 至少两个深入的工程问题案例，有具体代码改动与可检查的定位依据。
- [ ] 对启动、Flash、ISO-TP/UDS和恢复机制能从源码解释；至少三处关键设计有依据。
- [ ] 各关键参数清楚标记为**原厂规格 / 本项目编译结果 / 本项目软件测试 / 第三方参考 / 理论估算 / 硬件实测**之一。
- [ ] 文档所写状态与仓库实际状态一致；不以目录存在或README描述作为功能完成依据。
