# 项目技术深度与面试验收标准

## 一、为什么不能只做“CAN传BIN、写Flash”

开源示例已有ISO-TP、UDS下载、Flash写入、CRC及APP跳转。单纯复现标准流程区分度有限。本项目不追求车规量产，而是重点实现**可靠的升级事务状态机、Flash边界保护和失败恢复**。

## 二、最终应交付的技术能力

| 模块 | 核心能力 | 关键追问 |
|---|---|---|
| Bootloader启动 | 镜像检查、恢复入口、正确APP跳转 | Cortex-M复位、MSP、VTOR、中断清理 |
| Flash管理 | 预留分区、扇区擦写、写后读回和地址保护 | 单Bank约束、对齐、擦写时序 |
| 升级事务 | 会话、下载、顺序写入、完成校验与提交 | UDS 0x10、0x34、0x36、0x37、0x31 |
| ISO-TP | 多帧重组、流控、超时和序号异常处理 | SF、FF、CF、FC、STmin、BS |
| 异常恢复 | 断点、CRC错误、未提交标志、重复块处理 | 元数据最后提交、幂等与重试 |
| 升级工具 | 版本查询、刷写、进度和失败原因输出 | 跨端协议一致性 |

## 三、至少形成两个经验证的调试案例

- 启动跳转问题：通过源码分析和可执行实验研究MSP或VTOR错误；只有实际发生时才称为HardFault。
- UDS/ISO-TP通信问题：构造序号错误、流控超时、重复请求，定位和改进状态机。
- Flash/元数据问题：构造写入失败与CRC错误，验证无法启动损坏固件以及可重新刷写。

每个案例记录触发、日志、根因、修改、回归以及验证局限。借鉴外部案例必须注明来源。

## 四、可选加分项
基础版成熟后可选做软件双APP槽与启动回滚，或固件签名；不要求同时进行。STM32F407是单Bank，软件双槽不等于双Bank。

## 五、面试完成度判断
- 不依赖背稿能解释所有关键代码与控制路径。
- 至少提出并验证三项设计取舍。
- 有两个可复现的修改及故障回归案例。
- 源码、文档、测试记录和当前实现状态相互一致。
