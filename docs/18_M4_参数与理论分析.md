## 三、ISO-TP帧数与理论吞吐上限

经典CAN正常寻址下，8字节帧可承载：
- 单帧：最多7字节UDS应用数据；
- 首帧：6字节应用数据（其余2字节为PCI）；
- 连续帧：每帧7字节应用数据（其余1字节为PCI）；
- 多帧开始时，需要1个FC流控帧。本项目接收端BS=0，不在每个连续帧块后重复FC。

对于**完整的256B固件数据块**：

`0x36`的UDS请求 = 1B服务号 + 1B块序号 + 256B数据 = **258B**。

- FF = 1帧，承载6B；
- CF = `ceil((258-6)/7)=36`帧；
- FC = 1帧；
- 设备的`76 seq`应答 = 1帧；
- 共 **39个经典CAN帧**。

对经典CAN标准数据帧DLC=8，在不考虑位填充、额外重试及仲裁延迟时，每帧含帧间隔按**111位**计算。本项目假定相关帧均补齐至DLC=8。500kbit/s时：

`T_0x36_min=39×111/500000=0.008658s=8.658ms`。

`256/0.008658≈29568 B/s≈29.6kB/s`，只是**0x36传输阶段的理论上界**，不能写成整个升级流程的实测速度。

举例：M4 ARM GCC构建的APP镜像为**3188B**。按12个256B块+最后116B块计算，共13块；前12块每块39帧，最后116B块的请求PDU为118B，需1FF+16CF+1FC+1响应=19帧，总共 **487帧**。于是：

`T_min=487×111/500000=0.108114s`，即**约108.1ms**的0x36相关总线最短占用时间。

**关键排除项：** 不包含建立编程会话、0x34擦除、0x37提交、0x31镜像校验、系统重启；不包含位填充、仲裁等待、总线重发、Flash写入、软件调用开销和STmin。故**实际总升级时长只能更长**，而不是“3184B程序大约0.1秒就刷完”。

理论计算工具与公式测试：`python3 tools/estimate_upgrade.py 3188`、`tests/test_estimate_upgrade.py`。

ISO-TP分帧参考：[Linux内核ISO-TP说明](https://www.kernel.org/doc/html/v6.18/networking/iso15765-2.html)，以及项目实际`protocol/src/isotp.c`。

## 四、Flash擦写耗时如何合理论证

ST官方资料：[STM32F407VG数据手册](https://www.st.com/resource/en/datasheet/stm32f407vg.pdf)、[RM0090参考手册](https://www.st.com/resource/en/reference_manual/rm0090-stm32f4xx-reference-manual-stmicroelectronics.pdf)。

**不能直接从其它STM32F4型号、其它电源电压、或有外部VPP条件的擦写典型值，照抄成当前3.3V无外部VPP的实测结果。**

计算总升级耗时的工程模型应为：

`T_upgrade = T_session + Σ(T_erase_sector) + T_transfer_and_program + T_final_crc + T_restart`

其中`T_transfer_and_program`还包含分块正响应、等待时间和Flash编程，不能简单等于上面的108ms。当前已实现按扇区的`0x78`调度，但**真实F407扇区擦除最大时间及P2*约束**未得到上板验证。若真实擦除时间超过5s，当前协议与上位机超时需要进一步设计，而非通过任意编造“实际耗时”解决。

## 五、每个数字被追问时，先回答来源

- 原厂规格：ST官方文档与型号具体版本；
- 编译占用：ARM GCC输出、对应提交和优化选项；
- 软件注入：可复查的输入、日志、断言及C/Python源码；
- 理论估算：公式、假设、排除项；
- 真实硬件数据：**当前没有**。

这可以避免把“芯片最高频率168MHz”说成项目当前运行频率，也避免把“CAN波特率500kbit/s”误讲成已实测总线速率。
