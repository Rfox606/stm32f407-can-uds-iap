# M4补充：硬件验证依据、软件证据与现场排查手册

2026-11-24。基线 M4 PR #8；本阶段**没有开发板**，不能完成物理实验。四条主线分别采用实际源码、原厂规格、第三方公开案例、可执行的软件故障注入。以下区分「本项目软件已验证」「原厂规格」「理论推导」「第三方案例」「待实物验证」，不将任何参考项目的波形、日志、测试成功率归到本项目。

## 1. CAN物理层及通信验证

### 实物方案与配置

STM32F407VGT6 CAN1：PB8 RX、PB9 TX、AF9；外接支持MCU 3.3V逻辑电平的高速CAN收发器（例如3.3V供电的SN65HVD230，须核对具体模块引脚与模式），通过CANH/CANL与USB-CAN适配器连接，并共地。两端各120Ω终端电阻；断电、确认无其它并联负载后，CANH与CANL间应约60Ω。确认收发器正常模式而非待机，不直接将MCU TX/RX连至CANH/L。

当前 `bxcan.c` 的CAN_BTR=0x001C0001：BRP=2，BS1=13，BS2=2，SJW=1；APB1标称16MHz，位速率500kbit/s，位宽2μs，采样点87.5%。ST DS8626 Rev12 的HSI精度在25°C条件为±1%，对应标称CAN速率495～505kbit/s；更宽温区误差更大，不能保证实际总线容差。实际产品可改为准确HSE晶振并重新核对APB1/TIM2分频，不能随意修改主频而沿用BTR和定时参数。

原厂/公开依据：[ST DS8626](https://www.st.com/resource/en/datasheet/stm32f405rg.pdf)、[RM0090](https://www.st.com/resource/en/reference_manual/dm00031020-stm32f405-415-stm32f407-417-stm32f427-437-and-stm32f429-439-advanced-arm-based-32-bit-mcus-stmicroelectronics.pdf)、[TI SLLA270 CAN物理层](https://www.ti.com/lit/an/slla270/slla270.pdf)。

### 上板操作与排查（预案，不是已运行结果）

在仅连接授权台架的Linux环境，USB-CAN适配器已驱动为can0后：

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 500000
sudo ip link set can0 up
ip -details -statistics link show can0
# 另一个终端持续记录实际时间戳与报文
candump -L can0 > capture.log
# 先只查询模式/版本
python3 -m host.flash_cli status --interface socketcan --channel can0
# 确认固件、地址、供电均正确再刷写
python3 -m host.flash_cli flash build-arm/app.bin --version 0x010002 --interface socketcan --channel can0 --reset
# 软件复位后查询模式和已提交版本
python3 -m host.flash_cli status --interface socketcan --channel can0
```

故障定位顺序：
1. 没有任何帧：断电测终端电阻、检查收发器供电/模式/共地；示波器先测PB9 TX，再测CANH/CANL差分及2μs位宽。
2. 有发送波形但没有成功发送：检查接收节点是否处于正常模式且能ACK、波特率、终端、电缆；观察CAN_ESR中的LEC、TEC、REC、BOFF，CAN_TSR中的RQCP0/TXOK0/TME0。ACK错误并不必然立即Bus-Off。
3. 总线上有0x7E0却无UDS回应：确认是标准数据帧、过滤器接受0x7E0、FIFO非空、ISO-TP长度与连续帧序号；首帧后看是否收到0x30 FC。
4. 只在0x34后停止：区分正常Flash耗时与错误。收到0x78表示操作处理中；核对相邻等待响应及最终0x74的间隔，而非直接判定丢包。当前M4采用应答暂存及TXOK门控，不在应答未确认时开始擦除。
5. 当前固件在持续发送错误时可能停止事务；ABOM只是控制器自动Bus-Off管理，不代表UDS事务或软件tx_fault会自动恢复。当前不是完整自动重连方案。

## 2. Flash擦写时序与计算

ST DS8626 Rev12 §6.3.12 表40（109–110页附近，按文档表号核对）：在普通32位编程、VDD=2.7～3.6V、无外部VPP条件下，字编程典型16μs、表列最大100μs；64KiB扇区550/1100ms、128KiB扇区1/2s。16KiB扇区250/500ms。最大值为特性评估数据，并非每颗出厂全测；字编程最大值按数据手册为10万次擦除后测量。RM0090 §3.6指出擦写期间同Bank Flash读取会阻塞，擦写时复位后的内容不可保证；HCLK必须至少1MHz。本项目16MHz满足该要求，但忙等待循环次数不是可靠的实际超时。

| 镜像/操作 | 典型值计算 | 表列最大值代入 |
|---|---:|---:|
| 64KiB元数据擦除 | 0.55s | 1.1s |
| 一个128KiB APP扇区擦除 | 1s | 2s |
| 3188B APP合计擦除（2扇区） | 1.55s | 3.1s |
| 256B块（64个字编程） | 1.024ms | 6.4ms |
| 3188B APP（797字） | 12.752ms | 79.7ms |
| 20B元数据（5字） | 0.080ms | 0.5ms |

每个扇区开始前发送0x78并确认TXOK；相邻应答间隔由单扇区擦除主导，表列最大2s小于P2*=5s。最大896KiB APP需元数据+7个APP扇区，擦除典型7.55s、表列最大代入15.1s；不能一次性等待全部擦除，因此分扇区设计有实质意义。0x36传输3188B镜像理论最短总线占用108.114ms；与典型擦除及字编程相加约1.67s，仅为**部分阶段模型值**；使用表列最大时间也不是整机最大耗时。未含CRC计算、位填充、仲裁、其它诊断服务、软件调度及重启。尤其0x37/0x31全镜像CRC在16MHz下的最长处理时间仍须验证；不能只根据擦除参数宣称所有P2*满足。

测量方案：在`hw_erase`、`hw_program`入口与完成时读取硬件TIM2_CNT，或用预留GPIO翻转由示波器捕获；硬件计数器不等同于CPU软件轮询次数。用candump实际时间戳对照0x78与0x74/0x77/0x71。SWD读Flash_SR检查BSY、EOP和错误标志；暂停CPU会改变协议时序，不能用断点停顿测通信耗时。记录供电、环境温度、镜像长度、扇区、主频及重复次数。不得用本页数据表替代实际测量。

## 3. APP软件交权及启动验证

现有源码：APP `app_uds_request(10 02)`→`reply_gate`确认0x50 02 TXOK→`boot_handoff_request`。SRAM末尾64B从两套链接脚本排除，初始MSP=0x2001FFC0。交权邮箱0x2001FFF0/0x2001FFF4写入0xB007F407及反码0x4FF80BF8，DSB后写AIRCR发SYSRESETREQ。Bootloader调用`boot_handoff_consume`，检查RCC_CSR的SFTRSTF（bit28）与两字一致性，然后清零邮箱和复位标志；有效交权时保持Bootloader，不能立即跳回有效APP。正常APP与Bootloader分别通过F152返回0和1；F150读元数据版本。

**当前证据**：ARM双固件向量检查、`tests/test_handoff_policy.c`的地址/复位标志7项纯逻辑测试、`test_app_handoff_uses_readonly_mode_polling`的Python顺序测试、M4应答门控测试。没有证明普通SRAM在实际供电及SYSRESETREQ下可靠保持。

实际调试预案（不能写成已完成）：
- 正常APP查询F152=0；发送10 02，观察50 02，随后通信短暂停顿。
- 预先在`boot_handoff_consume`入口设硬件断点，在不另行触发复位的条件下读取RCC_CSR(0x40023874)、0x2001FFF0的两个字；记录真实值。继续运行后确认邮箱被清除、F152=1。
- 完成刷写并发送11 01，查询F152=0、F150=新提交版本，结合APP LED/实际业务功能确认运行。只读版本号不能证明业务功能已改变。
- 如果又回APP，先看复位原因及邮箱，检查是否被startup清零、栈覆盖或未写入；如果跳转后异常，检查APP向量表地址、初始MSP、Thumb位、VTOR=0x08020000、CFSR/HFSR及（有效时）BFAR/MMFAR、故障栈PC/LR，再定位反汇编。最后`msr msp,r0; bx r1`不得存在旧栈尾声。
- 当前接收镜像MSP检查允许整个普通SRAM上界0x20020000，而M3/M4自有镜像固定为0x2001FFC0；第三方任意镜像可能未预留邮箱。生产化需统一镜像ABI/更严格校验，不能宣称任意APP均可可靠交权。

## 4. 断电恢复：本项目13种实际软件注入

使用真正的`iap_updater`和`iap_boot_select`，先提交旧版本，再给Flash接口包装故障注入：在六个擦写操作中途（修改一半前缀）或刚完成后返回错误并停止事务，随后丢弃易失更新状态重新判断Flash。旧/新镜像各512B，两个256B写入块。另包含开始前尚未擦除的对照。中途前缀模型是人为构造，不代表芯片实际掉电时位变化的概率或形式。

| 中断点 | 操作中途 | 操作完成后但事务中断 |
|---|---|---|
| 0：未开始擦写 | — | 旧APP有效 |
| 1：擦元数据 | 恢复模式 | 恢复模式 |
| 2：擦APP扇区 | 恢复模式 | 恢复模式 |
| 3：写第一块 | 恢复模式 | 恢复模式 |
| 4：写第二块 | 恢复模式 | 恢复模式 |
| 5：写元数据正文 | 恢复模式 | 恢复模式 |
| 6：写最后Magic | 恢复模式 | 新APP有效 |

**真实软件执行结果：13/13通过；每种场景均检查Bootloader区测试字节保持不变，并重新全量刷写成功。** 旧固件在尚未破坏前可能仍有效；完整新镜像且最终Magic已落盘，即使确认丢失仍可能启动新APP。不能概括成“任何断电都进恢复模式”，也不能称旧APP自动回滚。实际断电在Flash忙时可能造成更复杂的数据异常，参照RM0090限制；本项目没有物理故障覆盖率或断电可靠性统计。

[完整软件日志](../evidence/M4-hardware/power_cut_matrix.txt)；[CI](https://github.com/Rfox606/stm32f407-can-uds-iap/actions/runs/45306810646)。

实物验证：使用独立控制的稳定台架电源，确认断电时不会经调试器/收发器反向供电；每个阶段分别做独立中断（擦元数据、擦APP、传输、校验提交、Magic写前/后），恢复供电后先读模式、元数据和镜像校验状态，再按需全量刷写。只在台架进行，不对车辆或生产设备试验。记录供电波形、实际触发时间、Bootloader/APP观察和重复次数。不得把软件模型的13/13写成真实物理断电成功率。

## 5. 第三方公开工程案例（仅对照）

[GamzeAkcay/stm32-uds-bootloader](https://github.com/GamzeAkcay/stm32-uds-bootloader) README报告STM32F407G-DISC1、Raspberry Pi/SocketCAN、500kbit/s及36KiB镜像的实验。作者记录20次计入的端到端刷写成功，另有前置等待超时尝试；采用64B块、不同地址/提交协议，优化帧间延时后约4.4–4.5s（约8.1KB/s），擦除约2s。两次人工断电分别发生在擦除和传输中；另一次是客户端中止，不是真断电；没有在元数据逐字提交时做真实断电。作者还公开分析过MSP改写后编译器栈访问引发HardFault的实例。**这些均为该作者的自述实验，不是本项目测试，不直接移植耗时、故障寄存器或成功率。** 可用于理解与本项目相同的设计问题，不能照搬其电平不合规的接线。

## 6. 面试时怎样回答

- CAN不通：从物理层、控制器错误状态、ID过滤、ISO-TP、UDS逐层定位。当前有实际C报文日志，可解释完整字节和FC/SN；没有实物示波器记录。
- Flash为什么慢：用原厂64/128KiB擦除数据和当前分区解释0x78/P2*，不要把固件只有3KiB等同于只擦3KiB。区分理论与真实耗时。
- 为什么要SRAM邮箱：APP先确认诊断请求，再软件复位让Bootloader获得独立Flash操作环境；保留区域防止栈覆盖，结合复位原因和一次性消费避免误进入。
- 断电怎么办：先失效元数据、再擦写APP、最后提交Magic；没有旧APP回滚，恢复靠Bootloader全量刷写。说明已实际执行的13种软件中断模型及两种有效镜像边界情形。

**最终边界：** 这份报告补足可核对的资料依据、完整报文字节、断电模型、现场操作步骤和理论数据。四项真实硬件实验仍未开展，不能出具物理验证合格结论。
