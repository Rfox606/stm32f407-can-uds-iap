# M1：实际开发问题与排查记录

本文件只记录本项目开发过程中实际观察到的编译问题，或经代码审查确认的设计缺口。不把设计推导写成已经在开发板上观察到的硬件故障。

## 问题一：无标准库的ARM交叉编译找不到string.h

**触发环境：** 使用Clang 17、--target=arm-none-eabi、-nostdlib对M0更新核心及STM32底层代码进行首次交叉编译。

**实际现象：** src/updater.c第6行包含string.h时，编译器报告：

    fatal error: 'string.h' file not found

**定位过程：** 主机端GCC测试可编译，ARM目标编译失败，说明不是代码拼写问题。检查构建参数后发现当前Clang工具链没有ARM目标的C标准库头文件和运行库，且链接选择了-nostdlib。M0源码用到了memcpy、memset、memcmp，即使绕过头文件错误，最终也需要对应实现。

**修复内容：** 新建 ports/stm32f407/include/string.h，仅在ARM固件构建时加入头文件搜索路径；在ports/stm32f407/src/runtime_mem.c提供三个最小内存操作的C实现。主机测试继续使用系统标准库，两套构建互不干扰。

**复查：** Clang ARM交叉编译通过，生成boot.elf和app.elf；两组实际向量表的MSP、复位入口检查通过。GitHub ARM GCC独立构建也通过。这个结果只能证明软件构建与链接正确，不代表上板运行。

**设计取舍：** 也可以安装ARM newlib并链接其运行库；本项目M1启动工程只需要少数内存函数，使用可审查的最小实现使Bootloader依赖较少，并避免启动阶段额外运行时初始化。

## 问题二：初始APP烧录缺少有效性元数据（设计审查发现）

**发现原因：** M0的iap_image_validate()不仅检查APP向量表和CRC，还必须读取扇区4中的20字节镜像元数据。如果初次使用SWD只写入Bootloader和APP而不写元数据，即使APP本身已经正确链接，启动决策也会按设计留在恢复模式。

**修正：** 新增tools/make_factory_metadata.py，从实际编译出的app.bin生成镜像大小、CRC32、版本号、元数据CRC及最后提交标志；在构建脚本中自动生成app_factory_meta.bin，并明确三个文件分别烧录至0x08000000、0x08010000和0x08020000。

**软件证据：** 对当前Clang编译得到的688字节APP，生成的元数据为20字节，工具检查初始MSP和复位入口。其CRC32与本次APP匹配。尚未进行开发板首次烧录，不宣称观察到了硬件启动失败。

**启示：** 系统初次部署和后续在线升级是两条不同的固件交付路径，二者都必须维护一致的元数据与有效性约定。
