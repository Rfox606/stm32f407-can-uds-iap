# M2：CAN / ISO-TP / UDS固件升级协议实现与验证

> 范围：STM32F407VGT6 的常驻Bootloader，经典CAN 500 kbit/s，单APP槽。**当前已完成ARM交叉编译和软件协议测试，未进行真实CAN物理总线、Flash擦写或断电测试。**

## 1. M2实际完成的模块

| 模块 | 文件 | 已实现内容 |
|---|---|---|
| bxCAN底层 | `ports/stm32f407/src/bxcan.c` | CAN1寄存器初始化、PB8/PB9复用、标准帧过滤、收发邮箱轮询、TX结果判断、TIM2毫秒时间基 |
| ISO-TP | `protocol/src/isotp.c` | 单帧、首帧、连续帧、流控帧；序号、BS、STmin、超时；固定320字节缓冲 |
| UDS刷写服务端 | `protocol/src/uds_boot.c` | 会话、版本读取、请求下载、传输数据、结束传输、镜像校验、复位、诊断仪在线保持 |
| 固件更新核心 | `src/updater.c` | 新增准备事务和逐扇区擦除接口，保留原有一次性擦除兼容路径 |

| 软件测试 | `tests/test_m2_protocol.c` | 分帧接收与发送、FC流控与间隔、错误序号、超时、正常刷写、CRC故障、幂等重复块、延迟镜像校验 |

**协议实现定位：** 本项目只实现升级所需的UDS/ISO-TP子集，不声称通过完整ISO一致性认证。研究过MIT许可的 `driftregion/iso14229`，本阶段实际采用较小、边界清晰的定制实现，便于讲清状态机及Flash时序；未把第三方库代码当作本项目实现。

## 2. CAN和时间基准

- STM32F407的bxCAN控制器CAN1：PB8为CAN1_RX，PB9为CAN1_TX，均配置为AF9。实际使用必须接外置CAN收发器和正确的终端电阻。
- M1时钟配置是16 MHz HSI，M2相应设定APB1为16 MHz：CAN分频2、BS1=13、BS2=2、SJW=1，总计16时间片，对应理论500 kbit/s，采样点87.5%。
- TIM2以16 MHz/16000=1 kHz提供毫秒计数。计数器可以在CPU等待Flash操作时计数，但是否满足实际硬件时间精度需上板验证。
- 诊断请求标准11位标识符为`0x7E0`，正负响应由`0x7E8`发出；使用经典CAN，不是CAN FD。
- 目前使用前台轮询处理CAN，单次Flash擦写期间不持续处理帧，因此诊断工具必须遵守“请求—响应—继续”节奏。
- HSI在极端电压/温度下的CAN时钟容差，需要根据数据手册确认；实际产品通常优先考虑准确的外部时钟。

## 3. 升级的UDS服务及确切字节约定

| 请求服务 | 用途 | 本项目格式与约定 |
|---|---|---|
| `0x10` | 编程会话 | `10 02`进入，`10 01`退出；正响应包括P2和P2*参数 |
| `0x22` | 查询数据 | `22 F1 90`返回元数据版本号（4字节），不等于重新验证整包CRC；`22 F1 91`返回升级状态与已写入字节数低24位 |
| `0x34` | 请求下载 | `34 00 44 + 4字节大端地址 + 4字节大端长度`，地址固定为`0x08020000`，长度8～917504字节 |
| `0x36` | 数据传输 | `36 + 1字节块序号 + 最多256字节固件`；序号从1开始，按8位自然回绕，重复同一块需与Flash读回内容完全一致 |
| `0x37` | 结束传输 | `37 + 4字节大端CRC32 + 4字节大端版本号`；后8字节是**本项目定义的厂家扩展参数**，并非所有UDS设备通用 |
| `0x31` | 镜像校验例程 | `31 01 FF 01`，先返回`7F 31 78`，再进行整包校验，最后返回`71 01 FF 01 + 结果码`（0=通过，1=失败） |
| `0x11` | ECU复位 | `11 01`，先等CAN正响应确认发送完成，再请求系统复位 |
| `0x3E` | 保持会话 | `3E 00`；不含抑制正响应位的其它变体 |

`0x34`的正响应为`74 20 01 02`，表示接下来`0x36`报文最大长度为258字节（含服务号和块序号）。`0x37`上传的CRC32采用IEEE反射多项式，必须与设备端的`iap_crc32`一致。大端格式用于UDS字段，固件BIN本身按原始字节写入。

**当前不含`0x27`安全访问，也没有固件签名或防降级；不应宣称升级访问受到认证保护。**

## 4. 为什么不直接在0x34里一次擦除Flash

`0x34`请求经过ISO-TP重组后，UDS层首先**准备事务但不执行擦除**，返回负响应`7F 34 78`（请求已接受、响应待处理）。Bootloader检查该CAN帧已经成功完成发送，才开始擦除元数据扇区4。

每完成一个扇区擦除，先返回新的`7F 34 78`，等待其完成发送后再擦下一个扇区。全部扇区擦完才返回`74 20 01 02`。此后才允许发送`0x36`数据块。

这样让Flash耗时操作发生在明确的响应窗口内，避免在CAN接收中断里操作Flash。STM32F407是单Bank Flash，擦除时读取Flash代码会受阻；分阶段等待机制可降低协议超时风险，但**尚未通过实物确认每个扇区的最长擦除时间均在P2*预算内**。

参数：UDS会话S3=5100ms、P2=50ms、P2*=5000ms；ISO-TP连续帧/流控等待超时=1000ms，FC WAIT最多3次。对于Flash擦除这样的长操作，更新S3计时基准，不能拿擦除开始之前的时间立即判定会话超时。

## 5. 如何处理0x36重复块

连续数据块的绝对写入偏移由`updater.written`决定，**UDS块序号只是8位协议计数器**：

1. 计数器等于期望值：写Flash、读回核对、更新绝对偏移，最后回应`76 + 块序号`。
2. 计数器等于上一个已确认块：重新读取该Flash区间，检查长度与字节内容是否完全相同，相同则再次确认，**不重复编程**。
3. 其余序号或重复块内容不同：返回`7F 36 73`。
4. Flash写入失败：不推进写入偏移；返回编程失败，等待诊断工具重新开始或按规则处理。

因此，主机发送数据后丢失肯定响应，不会因为重发同一个正确数据块而重复写Flash。该行为已有软件测试，不等于实物丢包测试。

## 7. 已知限制与M3接口

- **没有实物联调**，包括实际CAN波形、物理层接线、Flash擦写耗时与断电场景。
- 当前APP没有常态UDS诊断/交权接口；要进入Bootloader需在上电时按住PA0，或先让固件无效。M3可考虑APP发起的软件升级交权。
- 当前UDS服务支持升级流程子集；没有完全覆盖ISO-TP所有变体、完整安全访问、功能寻址或车规超时一致性。
- CAN发送失败后保守停止推进擦除，避免在未确认发送`0x78`时执行Flash操作；自动错误恢复仍需后续研究。
- `0x22 F1 90`返回已提交元数据的版本（含元数据CRC），`0x31`负责更重的全镜像内容校验。
- M3上位机必须按上述明确的字节约定编写，特别是`0x37`的厂家扩展CRC和版本字段；不能直接假设任何通用刷写工具无配置即可兼容。

## 9. 理论传输效率与实际程序体积

### 256字节固件数据块的传输下界

一次 `0x36` 传输256字节固件时，UDS请求本身含服务号、块序号，共258字节。经典CAN、ISO-TP正常寻址下：

- 首帧携带6字节应用数据；
- 剩余252字节，由36个连续帧承载（每帧7字节）；
- 数据方向共37个CAN帧，另有一帧接收方流控和一帧 `0x76` 正响应，共39帧。

以标准11位标识符、8字节有效载荷帧估算，每帧含帧间间隔至少约111位。仅计算上述39帧的物理传输最小比特数为 `39×111=4329位`，波特率500 kbit/s时对应**约8.66毫秒**，理论有效固件吞吐上界约**29.6 kB/s（十进制）**。

这只是忽略位填充、仲裁、帧间额外空隙、ISO-TP软件调度、Flash写入与确认等待后的**总线理论上界**，不是实测升级速度。实际速度通常低于此值。上述计算还假定CAN帧填充为8字节，这是本项目发送端的做法。

### 最新ARM GCC构建（2026-11-23）

- Bootloader：**5920字节**（含CAN、ISO-TP、UDS和Flash驱动）。
- APP演示固件：**668字节**。
- Flash分区预算：Bootloader 64 KB；元数据 64 KB；APP 896 KB。
- 两个固件均成功完成ARM GCC链接和向量表检查。来源：[本分支M2 ARM构建记录](https://github.com/Rfox606/stm32f407-can-uds-iap/actions/runs/45154912906)。

以上是该提交与编译配置对应的二进制大小，后续修改代码后应重新取最新结果。不能把这两个最小演示程序的占用当作量产程序体积。

STM32F407的Flash操作时长应以[ST STM32F407数据手册](https://www.st.com/resource/en/datasheet/stm32f407vg.pdf)相应电压、温度及PSIZE条件下的典型值/最大值分析；当前没有硬件实测擦除耗时。
