# M3：Python刷写、APP软件交权与具体开发问题

日期：2026-11-23。分支：`feature/m3-host-updater`。

## 一、从架构到代码的实际功能

| 模块 | 关键源码 | 实现作用 |
|---|---|---|
| Python固件解析 | `host/uds_client.py` 的`Firmware.open` | 校验固件尺寸、初始MSP及复位入口，计算CRC32和SHA256 |
| 诊断客户端 | `host/uds_client.py` 的`UdsClient` | 会话、软件交权、块序号、重试、CRC、版本回读与复位 |
| 物理CAN接口 | `host/can_link.py` | `python-can`连接CAN适配器、`can-isotp`负责分包和流控 |
| 命令行入口 | `host/flash_cli.py` | `inspect`、`status`与`flash`三类命令 |
| APP诊断入口 | `ports/stm32f407/src/app_uds.c` | 版本和运行模式查询、编程会话正响应、交权请求 |
| SRAM交权 | `ports/stm32f407/src/boot_handoff.c` | 写入双字标志→软件复位→Bootloader检查原因并消费标志 |
| 软件联调桥 | `tests/uds_bridge.c`、`host/bridge_link.py` | Python直接驱动真正C版UDS和更新核心，Flash由测试接口提供 |

**链路完整流程：**

```text
APP模式F152=0
    │ 10 02：APP先回50 02，等待CAN发送完成
    ▼
写保留SRAM标志、SYSRESETREQ
    │ Bootloader检查软件复位标志与完整双字标志
    ▼
Bootloader模式F152=1
    │ 10 02 → 34 00 44 addr size
    │ 7F 34 78（每次擦除前确认上一次响应已发送）
    │ 74 20 01 02（擦除完成）
    │ 多次36 seq payload（最多256B，重复相同块可再次应答）
    │ 37 CRC32 version → 7F 37 78 → 77
    │ 31 01 FF 01 → 7F 31 78 → 71 01 FF 01 00
    │ 22 F1 50（确认提交的版本）
    ▼
可选11 01：Bootloader正响应后系统复位→尝试启动有效APP
```

M3重新定义厂家自定义DID：`F150`为版本、`F151`为升级状态、`F152`为运行模式，避免占用标准`F190`（车辆VIN）、`F191`（车辆厂家ECU硬件号）、`F192`（系统供应商ECU硬件号）。参考[UDS Data Identifiers](https://uds.readthedocs.io/en/latest/pages/knowledge_base/did.html)。

**运行时版本说明：** F150读取的是已提交元数据中的版本号，其CRC与元数据本身匹配。APP内部还保存静态版本信息，两者目前没有强制一致性检查；不能把单纯修改元数据版本号表述成APP业务功能已发生变化。

## 二、没有实体开发板时，实际做了什么验证

使用`cmake -S . -B build && cmake --build build && ctest --test-dir build --output-on-failure`执行五个软件测试套件：

1. 固件更新核心：正确写入、CRC错误、无效入口、中断提交等。
2. STM32F407 Flash分区边界：地址范围、扇区大小及Bootloader保护区。
3. ISO-TP/UDS协议：分帧、流控、序号、超时、重复块与延迟响应。
4. APP交权策略：双字标志、软件复位原因、预留SRAM范围的纯逻辑检查。
5. Python/C协议联调：正常升级、`0x36`确认丢失、镜像损坏、模拟运行时状态丢失后再次升级、块序号255→0等。

其中第五项由`tests/uds_bridge.c`直接调用项目真实的`uds_boot_request`、`uds_boot_erase_step`、`uds_boot_finish_step`及`iap_updater`。**不是伪造UDS设备返回预设答案。** 但它绕过真实bxCAN和实际STM32 Flash寄存器，不等于完整硬件链路得到验证。

详细Python测试用例：`tests/test_host_updater.py`。GitHub对应自动化测试提供执行记录，不从第三方项目借用测试结果。

## 三、M3过程中值得面试深入的问题

### 问题一：0x37执行完整CRC导致响应过慢（代码审查发现）

**发现：** M2版本的`0x37`直接在UDS请求处理函数中执行`iap_updater_finish`，其中包含全镜像CRC扫描和Flash元数据写入。真实Flash操作可能耗时较长，导致诊断工具等待响应超时。

**修改：** 由同步`0x37`改为先回`7F 37 78`，确认上一CAN响应发送完成，再由`uds_boot_finish_step`执行实际校验和提交，最后响应`77`或`7F 37 72`。软件测试对应同步修改。注意P2*超时仍需硬件核算。

**代码：** `protocol/src/uds_boot.c`、`ports/stm32f407/src/boot_main.c`、`tests/test_m2_protocol.c`。

### 问题二：只有Bootloader可接收诊断指令，正常APP无法在线进入刷写（设计缺口）

**发现：** M2在有效APP时启动后直接进入APP，而APP只有LED演示，没有CAN接收和编程会话。这样无法仅靠CAN开始第二次升级。

**修改：** 在APP中加入小型CAN/ISO-TP诊断入口；当APP收到`10 02`，先发正响应，确认CAN发送成功后写入保留SRAM标志并执行软件复位。Bootloader同时检查RCC软件复位原因和双字标志，仅当条件都成立时留在升级模式。

**保护：** Bootloader和APP均预留SRAM末尾64字节，初始MSP改为`0x2001FFC0`，避免新栈覆盖标志；邮箱位于`0x2001FFF0`，每次进入Bootloader后清零，以避免反复进入刷写模式。

**验证范围：** ARM交叉编译与纯逻辑复位标志单元测试通过；还没有硬件证明SRAM在具体供电和复位条件下可靠保留。

### 问题三：错误使用UDS标准定义的DID（公开标准核对发现）

**问题：** M2把`F190`当作版本号、`F191`当作升级状态，又把`F192`用于运行模式。但这些编号本来已分配了标准含义，尤其`F190`为VIN。

**修正：** 统一迁移到厂家自定义范围中的`F150/F151/F152`，并同步修改C服务端、APP端、Python客户端和回归测试，不能只改文档。

**依据：** [UDS DID说明](https://uds.readthedocs.io/en/latest/pages/knowledge_base/did.html)，以及本仓库相应代码提交。

### 问题四：0x36确认响应丢失，是否能安全重传？（软件故障注入）

**触发：** C协议联调桥支持参数`--drop-36-once`，真实执行一次C版`0x36`写入，但故意不把正响应转交给Python。

**现象：** Python收到超时，重新发送**完全相同**的数据块。设备端比较上一个块的长度和Flash读回数据，一致则再次返回`76`，不会重复编程。

**验证：** `tests/test_host_updater.py`中的确认丢失测试与C桥接代码；可定位到更新核心的`written`、UDS的`last_seq/last_offset`。这只是软件注入，不是实物总线丢包。

### 问题五：固件下载中途丢失运行时状态（软件故障注入）

C联调桥`--reset-after-second-block`在已写入两块后清空C版UDS易失状态，但保留Flash数据。下一块请求被拒绝；Python明确报错。重新开始编程会话与`0x34`擦除后，可再次完整刷写。单槽无法恢复旧APP，但应保留Bootloader重新升级。

### 问题六：APP扩展CAN诊断后，ARM固件链接阶段出现未定义引用（实际发生）

**现象：** 向APP增加CAN/ISO-TP接收与升级交权代码后，第一次GitHub ARM交叉构建失败。编译器已完成源文件编译，但链接器报告`undefined reference to bxcan_send_response`、`isotp_init`、`app_uds_request`、`boot_handoff_request`等错误。

**定位：** 检查当次链接命令与`tools/build_firmware.sh`的APP目标源码列表，确认原构建脚本仍只加入`app_main.c`，没有把新增的CAN、ISO-TP、APP诊断服务和交权模块加入APP链接目标。不是函数声明缺失，也不是STM32寄存器错误。

**处理：** 更新构建脚本，将`bxcan.c`、`isotp.c`、`app_uds.c`、`boot_handoff.c`及CRC依赖纳入APP构建。再进行ARM交叉编译、生成ELF和BIN并检查向量表。

**证据：** [失败的ARM构建日志](https://github.com/Rfox606/stm32f407-can-uds-iap/actions/runs/45159785472)记录了实际链接错误；后续[通过的ARM构建](https://github.com/Rfox606/stm32f407-can-uds-iap/actions/runs/45160701634)保留修复结果。这是已经发生的软件工程构建问题，而不是虚构的板级HardFault。

## 四、参数表与性能边界

| 参数 | 本项目值 | 性质 |
|---|---|---|
| MCU | STM32F407VGT6，Cortex-M4，168 MHz最高主频 | 原厂型号规格，不是当前运行主频 |
| 当前系统时钟与CAN时钟 | 16 MHz HSI | 源码配置，尚待板级实测 |
| CAN位速率 | 500 kbit/s，标准11位标识符 | 根据CAN定时寄存器推导 |
| 请求/响应CAN ID | 0x7E0 / 0x7E8 | 源码配置 |
| ISO-TP诊断PDU上限 | 320字节 | 源码固定缓冲 |
| `0x36`数据载荷上限 | 256字节 | 设备端限制 |
| ISO-TP帧/流控等待 | 1000 ms | 源码参数 |
| UDS会话S3 | 5100 ms | 源码参数 |
| UDS响应P2 / P2* | 50 ms / 5000 ms | 响应声明值；实物时序待验证 |
| Python初始/待处理等待 | 2 s / 6 s，累计90 s | 默认客户端策略，保留可配置参数 |
| ARM链接目标 | Bootloader64 KB，APP896 KB | 设计容量，不是实际使用量 |
| SRAM交权保留区 | 64 B，初始MSP=0x2001FFC0 | 双工程链接脚本与代码 |

**程序实际Flash/RAM占用**：应使用当前提交的ARM GCC `size`、`map`和BIN结果；随代码改动而变化，不采用早期M2的最小固件数字。实际Flash擦写时长、CAN总线有效吞吐和升级总时间尚未测试；理论计算参考`docs/12_M2_协议实现与验证.md`。

## 五、尚未完成或需要硬件才能确认

- CAN收发器接线、时钟偏差、实物Flash编程和单Bank擦写期间的确切时序；
- SRAM标志在SYSRESETREQ后的保持及APP交权真正成功；
- 实际供电中断及Flash擦除中断对数据的影响；
- CAN总线关闭、仲裁错误、邮箱耗尽等复杂错误恢复；
- APP中的静态版本与Flash元数据版本自动一致性检查；
- 实物恢复模式入口、APP实际启动和最终升级总耗时。

**验收结论：** M3可以称作“软件协议与上位机已联调”，不能称作“实物CAN在线升级完全实测”。M4要围绕现有源码与真实记录开展深入面试技术复盘。
