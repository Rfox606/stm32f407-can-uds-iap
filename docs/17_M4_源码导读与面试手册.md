# M4：源码导读与嵌入式技术面试手册

> 依据本仓库M0–M4实际源码与CI构建结果。保留Bootloader、CAN、ISO-TP、UDS、MSP、VTOR等通用专有名词；其余尽量使用中文技术词。下面不是背诵材料的堆积，每一道题都能定位到实际源码。

## 一、项目背景，为什么值得做

传统开发时可以通过SWD烧写MCU，但设备装配、封装并部署之后，现场再接调试器可能成本较高。在线固件升级的目标是通过已有通信链路更新应用程序。本项目选择汽车电子常见的**经典CAN总线**，使用ISO-TP完成多帧传输，再由UDS规定编程会话和固件下载事务。MCU内部用常驻Bootloader管理Flash分区和镜像有效性，APP不直接重写自身。

**实际边界：** 个人项目验证了ARM可编译固件和完整软件协议链路，不宣称上板刷写、车规安全认证或A/B自动回滚。

### 60秒项目介绍（可结合实际工作调整）

> 我做了一套基于STM32F407的CAN/UDS固件升级系统，主要是把设备部署后的固件更新从SWD调试接口转换到CAN通信。整个工程分成常驻Bootloader、正常APP和Python升级工具三部分。Bootloader负责CAN接收、ISO-TP分帧、UDS编程状态机，以及Flash擦写和镜像CRC校验；正常APP能够通过诊断请求切换进入Bootloader。开发中重点处理了Flash擦除前的等待响应、0x36重复数据块、异常恢复以及启动跳转时的MSP和VTOR。代码已经完成ARM目标编译，Python升级工具也和C版UDS更新核心进行了软件联调，并对超时、重复块和CRC错误做了故障注入。真实硬件的CAN通信和Flash操作尚未做实物验证。

## 二、按调用顺序看一遍真正的数据流

```text
① Python读取BIN：host/uds_client.py::Firmware.open
     └─ 栈顶与复位向量检查 / CRC32 / SHA256
② 查询APP/Bootloader模式：UdsClient.get_mode -> 22 F1 52
③ APP若在运行：app_uds_request(10 02) -> 50 02
     └─ reply_gate 收到CAN TXOK -> boot_handoff_request
     └─ SRAM双字标记 + SYSRESETREQ -> boot_handoff_consume
④ 进入Bootloader编程会话：uds_boot_request(10 02)
⑤ 请求下载：uds_boot_request(34 ...) -> busy_erase
     └─ reply_gate确认 7F 34 78 已发送
     └─ uds_boot_erase_step -> iap_updater_erase_step
     └─ 循环至74 20 01 02
⑥ 每256B数据：ISO-TP收集到完整UDS PDU
     └─ uds_boot_request(36) -> iap_updater_write
     └─ Flash写入、读回比对 -> 76 seq
⑦ 37+CRC+版本 -> 7F 37 78 -> reply_gate TXOK
     └─ uds_boot_finish_step -> iap_updater_finish
     └─ 整包CRC、MSP、复位入口、元数据最后提交 -> 77
⑧ 31 01 FF 01 -> 延迟执行iap_image_validate -> 71 ... 00
⑨ 22 F1 50读取已提交版本；按需11 01软件复位
⑩ Bootloader有效性判断 -> boot_jump_to_app
     └─ 关闭SysTick、中断清理、设置VTOR、MSP、跳转Reset_Handler
```

关键模块：`ports/stm32f407/src/boot_main.c`、`protocol/src/uds_boot.c`、`src/updater.c`、`src/image.c`、`protocol/src/reply_gate.c`、`host/uds_client.py`。

## 三、面试中最应弄懂的18个追问

### 1. Bootloader和APP如何划分Flash？为什么？

`ports/stm32f407/linker/boot.ld`和`app.ld`明确Bootloader在`0x08000000`起、APP在`0x08020000`起；元数据放在`0x08010000`扇区4。F407的扇区大小不均匀：最前面4×16KB，之后64KB与7×128KB，因此把元数据单独放在64KB扇区虽然空间利用率不高，却能避免擦除元数据时破坏常驻Bootloader。APP最大896KiB；升级只能擦元数据和APP区，不能越界到0～3扇区。

### 2. 为什么不用两个APP槽位？

这个项目是单槽：Bootloader64KB、元数据64KB、剩余APP896KB。优点是简单、无需双份APP占用和镜像交换；缺点是升级中断后旧APP可能失效，不能自动回滚。恢复方式是保留Bootloader重新刷写，而非回退旧固件。

### 3. MCU上电后到底从哪里执行？

Cortex-M从初始向量表获取初始MSP和Reset_Handler入口。Bootloader使用`startup_stm32f407.S`复制.data、清零.bss，进入`boot_main.c::main`。先判断保留SRAM交权请求、手动按键及已提交镜像是否有效，随后进入APP或保持Bootloader恢复模式。

### 4. APP为什么不能直接从0x08020000开始链接却沿用默认向量表？

APP必须有自己对应的向量表、复位入口和链接地址；Bootloader跳转时通过`SCB->VTOR`迁移中断向量表。否则中断触发时可能仍使用Bootloader的向量。APP启动文件的.data加载地址也必须匹配APP实际链接段。

### 5. 改MSP跳转时可能有什么问题？

在普通C函数中改写MSP之后，若编译器仍从新栈执行旧函数的返回序列，可能破坏控制流。因此`boot_jump.c`最后由`naked`函数执行`msr msp,r0`后直接`bx r1`，不再返回。此前在ARM反汇编中核对过指令顺序。此处是源码/反汇编检查，不是已发生的实物HardFault。

### 6. 为什么Flash写入前要擦除，为什么按扇区进行？

F407内部Flash编程不能任意把已写为0的位改回1，必须先擦除对应扇区。真实硬件的擦除粒度不是任意字节；`flash_layout.c`维护全部12个扇区的物理边界，`flash_stm32f407.c`限制可写区域。当前采用3.3V供电假设与32位编程并在写后读回。

### 7. Flash擦除期间CAN怎么办？

STM32F407是单Bank Flash，擦除时取指和中断服务可能受阻。因此`0x34`**先回`7F 34 78`**，确认CAN响应真正成功提交发送后，才擦一个扇区。每擦完一扇区继续回复等待响应，最终才`74`。理论上仍需对照真实扇区最大擦除耗时确认P2*预算，未上板验证。

### 8. M4为什么还要做reply_gate，之前不已经等TXOK了吗？

原程序只判断CAN邮箱“现在是否空闲”，没有证明本次应答已提交发送。假如`isotp_send`失败，空邮箱仍可能让后续擦除执行。`reply_gate`保存待发送UDS响应，等待真正的发送完成后发放一次性动作授权。测试通过了邮箱繁忙、发送失败和未TXOK等注入场景。**这是一条因果关系约束，而不只是超时参数。**

### 9. CAN、ISO-TP和UDS分别负责什么？

CAN负责物理/数据链路上的帧和仲裁；经典CAN单帧最多8字节。ISO-TP负责将超过一帧的数据拆成FF/CF并由FC流控、接收重组；UDS在ISO-TP应用数据上定义诊断会话、下载、传输、校验和复位等服务。`bxcan.c`→`isotp.c`→`uds_boot.c`对应这一层次。

### 10. 你们CAN的500kbit/s怎么配置？

M1选择16MHz HSI，APB1取16MHz；`bxcan.c`设置分频2、BS1=13时间片、BS2=2、SJW=1，一个位时间共16时间片，因此`16MHz/(2×16)=500kbit/s`，采样点`(1+13)/16=87.5%`。这只说明源码时序配置；真实时钟精度及CAN波形未实测。

### 11. ISO-TP的首帧和连续帧分别能放多少字节？

常规11位地址、经典CAN 8字节数据：首帧2字节协议控制信息，携带6字节应用数据；连续帧1字节控制信息，携带最多7字节；接收端发FC告诉发送端块大小BS与最小帧间隔STmin。该项目的每块UDS请求长度为2+256=258字节，对应首帧1、连续帧36、流控帧1以及0x76响应帧1，总计39帧。

### 12. UDS下载的核心服务有哪些？

`0x10`进入编程会话、`0x34`约定写入地址与长度、`0x36`按块序号传数据、`0x37`校验与提交、`0x31`验证提交镜像、`0x11`请求软件复位。项目还使用`0x22`查询厂家定义的版本与运行模式（F150/F152）、`0x3E`保持会话。`0x37`附带CRC和版本号是本项目扩展，不是所有UDS ECU默认采用的通用格式。

### 13. 0x36发送成功，但上位机没有收到0x76，怎么办？

可以按限定次数重发**相同**块。设备端保存上次块序号、绝对偏移和长度，并读取Flash核对内容，相同就重复回复0x76、不再次写入；不同就返回NRC 0x73。M3软件故障注入真正执行了一次C代码写入、丢弃确认，上位机重发后通过。

### 14. 八位块计数器回绕，会不会判断错？

`0x36`用8位序号，255后回到0。设备端不以这个序号计算Flash地址，而是用`updater.written`的32位绝对偏移，仅比较期望块和上一次块。主机对大于256块的镜像进行了跨回绕软件测试。

### 15. 为什么用CRC32，CRC足以保证安全升级吗？

CRC32检验数据传输/存储过程的意外损坏；它不是数字签名，不能证明固件来自授权来源。项目额外检查初始MSP、Reset_Handler以及元数据提交标志，以防无效程序被激活，但并没有签名验证或安全启动，不能宣称具备防恶意篡改能力。

### 16. 升级过程中断电，具体会怎么样？

由于元数据扇区在开始升级时先擦除，随后写APP，最后才写元数据有效标志，下载不完整时Bootloader通常不应该接受镜像。原APP可能已被破坏；重新上电应进入Bootloader恢复模式，再进行全量刷写。主机测试验证了模拟Flash中断，不是实物断电测试。

### 17. 不用硬件，如何证明这项目不是几个空函数？

实际源码可交叉编译生成分别链接的Bootloader和APP ELF/BIN/MAP；`tests/uds_bridge.c`真实调用C版UDS更新函数与Flash测试接口，Python客户端驱动完整下载，能够故意丢0x36响应、破坏CRC以及中途中断重新刷写。GitHub Actions保留构建日志和测试结果。需要说明它验证的是**软件协议逻辑**，不能替代真实CAN/Flash上板验证。

### 18. 做完后你还认为有哪些不足？

最重要的不足是单Bank Flash的真实擦写时序和CAN响应时限没有上板确认；其次是发送错误后的自动恢复、安全认证/签名、防回滚未实现；此外APP静态版本字段与元数据版本可分离，需要统一版本生成。个人项目先完成合理的可靠性机制和软件联调，后续按真实硬件验证结论决定是否继续拓展。
