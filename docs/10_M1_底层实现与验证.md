# M1：STM32F407底层工程实现与验证

## 一、已经编写的实际代码

| 模块 | 源码 | 职责 |
|---|---|---|
| 启动与中断向量 | ports/stm32f407/src/startup_stm32f407.S | Cortex-M4启动、98个向量条目、初始化.data和.bss、进入main |
| 链接脚本 | ports/stm32f407/linker/boot.ld、app.ld | Bootloader 0x08000000及APP 0x08020000独立链接 |
| Flash驱动 | ports/stm32f407/src/flash_stm32f407.c | Flash解锁、按扇区擦除、32位编程、读回、锁定、Bootloader区域保护 |
| 扇区检查 | ports/stm32f407/src/flash_layout.c | F407 4×16KB、1×64KB、7×128KB地址映射和合法范围检查 |
| APP跳转 | ports/stm32f407/src/boot_jump.c | 关闭SysTick、清理NVIC、VTOR迁移、MSP设置及无栈尾声跳转 |
| 主程序 | ports/stm32f407/src/boot_main.c、app_main.c | 依照APP有效性或PA0按键决定进入APP/恢复模式；PD12/PD13 LED演示 |
| 独立运行库 | ports/stm32f407/src/runtime_mem.c | 仅提供memcpy、memset、memcmp，固件不依赖标准库链接 |
| 初始固件元数据 | tools/make_factory_metadata.py | 生成与实际APP二进制大小和CRC一致的20字节元数据 |

中断向量顺序依据ST官方STM32F407启动模板，文件为本项目独立编写，并未直接复制厂商启动源码。M1目前采用少量直接寄存器操作，不依赖HAL。M2单独添加CAN和UDS。

## 二、构建与初次烧录准备

推荐执行：bash tools/build_firmware.sh；也可通过环境变量选择Clang/LLVM目标工具。

构建输出：boot.elf、boot.bin、boot.map、boot.disasm.txt、app.elf、app.bin、app.map、app.disasm.txt以及app_factory_meta.bin。构建脚本同时检查复位入口和初始MSP。

| 文件 | 初次外部写入地址 | 作用 |
|---|---|---|
| boot.bin | 0x08000000 | Bootloader，位于扇区0～3 |
| app_factory_meta.bin | 0x08010000 | 与APP内容绑定的元数据，位于扇区4 |
| app.bin | 0x08020000 | APP，位于扇区5起 |

必须保证APP元数据与其实际二进制严格匹配，否则Bootloader应保留在恢复模式。以上是计划的外部烧录步骤，尚未上板执行。

## 三、已经得到的证据（2026-11-23）

- 本地Clang 17针对Cortex-M4进行交叉编译及链接成功。
- boot.bin为2024 B，复位向量0x08000189，初始MSP 0x20020000。
- app.bin为688 B，复位向量0x08020199，初始MSP 0x20020000。
- 生成20 B APP元数据；本次Clang构建对应的APP CRC32为0x6795A92F。不同工具链构建结果应分别记录。
- 更新核心9个场景、Flash扇区及边界15项检查均通过；CTest 2/2套件通过。
- Clang反汇编确认transfer_msp_reset最终指令顺序为msr msp,r0，再执行bx r1，没有对新栈执行函数尾部恢复。
- 完整命令输出见 evidence/M1/clang_host_build.txt。另配置GitHub Actions ARM GCC独立编译，实际是否通过以远端记录为准。

## 四、真实工程约束及待验证

1. STM32F407采用单Bank Flash，擦写时的取指和中断处理受限。M2不能假设CAN收包可在擦除时正常持续处理，需要安排UDS等待响应和超时。
2. Flash x32编程模式仅适合2.7～3.6 V。当前设计板级电压假设是3.3 V。
3. 轮询最大次数仅用于避免无限等待，并不是准确的硬件时间测量。
4. Bootloader恢复模式尚无CAN接收功能；因此不能声称M1已经完成在线升级。
5. 未使用开发板验证Flash擦写、GPIO波形、实际APP跳转或断电恢复。
