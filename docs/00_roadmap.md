# 开发路线与验收标准

本项目先建立稳定的分层结构，再逐阶段完成实现。任何未完成的硬件环节都不能直接标记为已验证。

## M0：基础架构与核心算法（已完成）
- 确定STM32F407VG单APP槽Flash分区。
- 实现Flash抽象、固件接收、CRC32校验、有效性元数据和启动选择。
- 建立模拟Flash与9个主机端测试场景。
- 验收：CMake构建成功；9个场景通过；明确代码及证据边界。

## M1：STM32F407底层工程（软件完成，尚无硬件验证）
- 建立可编译的Bootloader和APP工程，加入自主编写的Cortex-M4最小启动文件、外设寄存器驱动及完整链接脚本。
- 实现Flash擦写、扇区保护、地址与对齐检查、写后读回。
- 实现跳转APP的中断清理、向量表重定位及栈指针设置。
- 验收：ARM交叉编译、链接映射和代码审查通过；若无硬件，不声称已实测启动跳转。

## M2：CAN/ISO-TP/UDS刷写（协议软件测试通过）
- 实现带固定缓冲的UDS/ISO-TP升级子集；参考成熟开源协议实现但未直接复制。
- STM32端接入bxCAN；设计编程会话、请求下载、数据传输、结束下载、校验和复位流程。
- 解决超时、错误块序号、重复块、流控和长耗时Flash操作之间的关系。
- 验收：协议输入输出与异常路径有实际测试记录。

## M3：升级工具与联调（已完成软件范围，尚无硬件验证）
- 已编写Python固件检查、模式查询、编程会话、刷写进度和有限重试工具。
- 通过Python与实际C版UDS/更新核心跨进程联调，验证正常下载、CRC错误、确认丢失重发、易失状态丢失后重新刷写和块序号回绕；增加APP软件交权源码及复位策略测试。
- 验收：保留可复现命令和日志；实物行为单独标注。

## M4：工程问题分析与面试准备（软件交付已完成）
- 增加CAN应答确认门控，并通过邮箱繁忙/提交失败/TXOK等待等软件注入；整理原有0x36重复块和链接错误等可复查案例。
- 完成源码导读、18项面试追问、参数分类、理论吞吐计算及明确的剩余风险清单。
- 验收：每项技术主张均能指向源码、测试或明确标注为设计分析。

## M5：可选
软件双APP槽位与启动回滚，或者固件签名验证。M0～M4完成后，再根据实际技术收益选择。
